# delivery-vrptw：带时间窗与电量约束的末端配送路径规划

精确 MIP 与 ALNS 对照、Solomon 基准对标、无人机能耗变体、随机仿真下的策略评估。

> 个人开源项目，2026 年 9 月新建；与任何过往实习或课程无关，与美团或任何公司无关联。
> 所有数字都由 `scripts/` 下的脚本跑出、写进 `results/*.json`，README 里的表格由
> `scripts/check_readme.py` 从这些 JSON 生成（CI 里 `--check` 不一致就失败）。

它们描述当时的实验，不代表新版已重跑全部 112 个小实例、56 个大实例和 1000 个仿真场景。

完整测试另行复核已存储的大实例路径。CI 保存当前提交的报告、测试 XML 和变异证据。

本轮修复了三类会影响结论的问题：非法节点编号被 Python 负索引接纳；零需求且同址客户
形成不连接仓库的子环；搜索缓存沿用修改前的需求或时间数据。多仓 I1 也会检查其他可用仓库，
不再因最便宜仓库不可用而直接丢弃客户。MIP 增加与货量无关的连通流，并在返回结果前独立
检查每个客户、路线闭合、物理约束和目标值；测试错误与真正检测到缺陷在变异报告中分开处理。

**English summary.** A from-scratch Python study of the vehicle routing problem with time windows (VRPTW)
and a delivery-drone variant (payload, payload-dependent battery energy with a reserve, time windows,
maximum trip duration, battery swaps at one or two depots). It contains an independent feasibility
checker (it reproduces all 56 published Solomon best-known solutions), Solomon's I1 insertion
heuristic as a baseline, an ALNS (Ropke & Pisinger style), and an exact 2-index MIP solved with HiGHS
that is certified against brute-force enumeration on tiny cases. ALNS is measured against proven MIP
optima on small instances and against the best-known solutions on the 56 Solomon 100-customer
instances; drone plans are then executed in a seeded discrete-event simulator with wind, service-time
noise and energy uncertainty, and static, buffered and rolling-replanning policies are compared with
paired scenarios and bootstrap confidence intervals. It is a portfolio/learning project, not a
production dispatcher and not a state-of-the-art solver.

<!-- BEGIN:en_findings -->
- Small Solomon subsets (first 10/25 customers, distance objective): HiGHS proved 90/112 optima; ALNS matched 88/90 of them with at least one of 5 seeds.
- 56 Solomon 100-customer instances, 10000 ALNS iterations x 3 seeds: 413 vehicles in total vs 405 for the best-known solutions; on the 48 instances with the BKS fleet size the best run is 1.97% longer on average.
- Drone variant (60 orders, 2 depots): ALNS changes planned energy by -4.9% on average vs Solomon I1 (fleet size is not in its objective).
- Simulation (1000 paired scenarios): on-time rate 90.4% (I1 plan), 91.1% (ALNS plan), 95.6% / 97.9% (ALNS with 15% / 30% buffers). Hourly rolling re-planning vs the 30% buffer: +0.4 pp on-time (95% CI -0.1 to +0.9), i.e. no clear gain.

## 问题定义

**输入与返回值。** 数据必须是形状一致的有限实数，距离、耗时、需求、服务时间及成本权重非负；
仓库需求为零。零需求、同位置客户、零容量、零车辆和空客户集都有定义，不依靠排除这些情况来保证连通。
构造函数保存自有只读数组，修改数据推荐 `dataclasses.replace(inst, demand=...)`；重赋可写数组后
搜索端停用对应缓存，求解与校验入口重新验证数据。不要复用旧实例的路线缓存作为新结果。
路线编号接受 Python/NumPy 整数，拒绝布尔、浮点、负数和越界编号；`evaluate` 支持一次性生成器，
将畸形路线记为不可行且不计入正常客户/费用统计。路线辅助函数对空仓库行程返回中性结果。

`solve_mip` 的 `valid` 表示路线通过独立复核；`optimal` 还要求求解成功、零 gap 且上下界一致
（浮点比较容差为绝对 `1e-6`、相对 `1e-7`）。默认请求零相对 gap，显式允许非零 gap 时不会
把仅有可行现解称为已证最优。无可行现解时 `routes`、`objective` 为 `None`；发现输出自相矛盾时
返回 `status=4` 和原因。`max_routes_per_depot` 显式覆盖实例的每仓车辆限制。

**VRPTW（Solomon 约定）。** 一个场站、`n` 个顾客，每个顾客有需求 `q_i`、时间窗 `[e_i, l_i]`、服务时长 `s_i`；
车辆容量 `Q`；早到可等待，服务开始不得晚于 `l_i`，须在场站关门前返回。距离为双精度欧氏距离、行驶时间 =
距离、不取整（与 SINTEF 的 BKS 表一致）。100 顾客实验用分层目标：先最少车辆数，再最短总距离；
小实例（前 10/25 个顾客）用单一的总距离目标（车辆数不限，≤ 25）。

**无人机变体（低空末端配送）。** 一个或两个场站；每个航次从某场站出发、送若干包裹后回到同一场站：

- 载重：航次包裹总重 ≤ 3 kg；
- 能耗：每段航线能耗 = 距离 × (a + b × 当前机上载重)，外加每航次固定起降能耗；载重随送货递减，
  所以顺序会改变能耗。线性于总质量的形式来自 D'Andrea (2014) 的模型
  `P = (m_机 + m_货)·v / (370·η·r) + p_航电`（η = 0.5 取自原文；r = 3、机身 7 kg、航电 0.1 kW、空速 54 km/h、
  起降 6 Wh、电池 250 Wh 是本项目的示意取值，**未对任何真实机型标定**）；
- 备用电量：落地时剩余电量 ≥ 20%（可用 200 Wh）；
- 时间窗、最长航次时长 45 分钟（出发时间可推迟以减少等待）；等待假定在地面、不耗电；
- 回场站换电 5 分钟后可再飞：先由 ALNS 规划航次（目标：总能耗 Wh），再用贪心“航次串联”把航次分给无人机，
  得到机队规模（这一步是启发式，不与路径联合优化）。
- 实例：`vrptw.drone.generate(seed)`，12 km × 12 km 区域，4 个热点聚类 + 20% 散点，60 个订单分布在 6 小时内，
  时间窗宽 30/45/60 分钟。全部为合成数据。

**随机仿真。** 按计划执行航次，场景随机量：日级风速 U(0, 7) m/s 与风向、逐小时扰动；地速按风矢量与航向计算，
飞行时间与能耗都乘以 `v_空/v_地`；每段航线再乘 LogNormal(0, 0.05) 噪声；投递时长乘 LogNormal(0, 0.3)。
所有策略共用同一组场景（共同随机数），逐场景做配对比较。

## 方法

| 模块 | 内容 |
|---|---|
| `vrptw/checker.py` | 独立可行性检查（顺序循环实现，不与搜索代码共享任何函数）：顾客恰好服务一次、容量、时间窗、回场时间、能耗与备用电量、最长航次时长、每场站车辆上限。用它复算 SINTEF 公布的 56 个 BKS 详细解，车辆数与距离（两位小数）全部一致（见测试）。 |
| `vrptw/construct.py` | Solomon (1987) I1 顺序插入，试 6 组参数 × 2 种种子规则取最好，作为贪心基线。 |
| `vrptw/routes.py` | 路线缓存最早/最晚服务开始时间、载重、累计能耗距离，插入可行性按位置 O(1) 判断并用 numpy 向量化；最长时长用“最晚出发 vs 最早出发 + 总等待”公式。 |
| `vrptw/alns.py` | ALNS：破坏算子 random / worst / Shaw / route removal；修复算子 greedy / greedy+noise / regret-2 / regret-3 / 按随机或需求/距离/截止时间顺序逐个插入（Christiaens & Vanden Berghe 2020 的 recreate 思路）；轮盘赌自适应权重（得分 33/9/13，反应系数 0.1）；模拟退火接受。分层目标用两阶段：先反复删一条路线并在少一辆车的上限下搜索，失败后固定车辆数优化距离。修复只会插入通过可行性检查的位置，插不进的顾客留在未分配池中。 |
| `vrptw/mip.py` | 2-index MIP（每客户消耗一单位连通流；时间/载重 MTZ 型大 M 约束；载重相关能耗利用“弧上载重 = r_j”线性化；多场站用顾客-场站标签；最长时长用每条路线的出发时间变量），`scipy.optimize.milp`（HiGHS）求解，独立校验现解后给出目标、界与 gap。 |
| `vrptw/brute.py` | ≤ 6 个顾客时枚举所有划分 × 排列 × 场站，用 checker 评估，用来验证 MIP。 |
| `vrptw/drone.py` | 能耗参数、实例生成器、航次串联。 |
| `vrptw/sim.py` | 离散事件执行、风场、指标、配对 bootstrap；滚动重规划策略。 |

## 这不是什么 / 局限

- 不是生产级调度系统：没有实时订单流接入、没有空域/航线/起降点容量约束、没有多无人机冲突避让。
- 不是最先进的求解器：纯 Python + numpy，每秒迭代数有限；在给定预算内与 BKS 仍有差距（见 1b），没有做
  Nagata–Bräysy 式的专门减车算子等强化。
- 能耗模型是简化的线性模型（稳态巡航功率 × 时间），参数示意性取值；悬停/爬升只用一个固定起降能耗近似；
  等待不耗电的假设偏乐观。
- 无人机实例全部是合成的（种子固定），没有使用真实城市地理数据。
- 航次串联（机队规模）是贪心启发式，ALNS 的目标里没有机队规模；两者没有联合优化。
- MIP 是教科书式 2-index 大 M 模型，只适合很小的实例；宽时间窗实例（R2/RC2/C2）在时限内常常证明不了最优。
- 仿真中计划一旦起飞就不改航；滚动策略只在整点重规划，风速预报用“当前观测 + 最不利航向”，没有真实预报模型。
- 迟到订单（订单在白天陆续到达）没有建模。
